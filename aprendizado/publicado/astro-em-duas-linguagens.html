Astro em duas linguagens

Você perguntou se o Astro “não carrega o JavaScript, e deixa em segundo plano”. Metade disso está certa — e a metade errada é justamente a que decide o seu orçamento de 15 KB.

A resposta curta, antes de tudo

Sim, o Astro entrega zero JavaScript por padrão. Mas não porque ele adia o JavaScript para segundo plano. É porque, na maior parte da página, o JavaScript nunca chega a existir. Ele roda uma vez, na sua máquina, cospe HTML, e some.

O “segundo plano” existe, mas é outra coisa — é um recurso que você liga à mão, componente por componente, escrevendo client:idle ou client:visible. Não é automático, não vale para a página inteira, e não tem nada a ver com “1 segundo”.

Guarde esta frase, porque ela é o eixo desta página inteira: adiar não é o mesmo que não existir. JavaScript adiado ainda pesa no seu orçamento. JavaScript que não existe pesa zero.

01 · A fronteiraOnde o JavaScript nasce e onde ele morre

Um componente .astro tem duas partes separadas por três traços — o frontmatter. Tudo que está acima dos traços roda uma vez, na sua máquina, durante o build. Tudo que sai abaixo é HTML.

“Astro components are HTML-only templating components with no client-side runtime. (…) They don't render on the client. They render to HTML either at build-time or on-demand.”

Fonte primária: Astro Docs — Components

Aquele bloco cercado pelos traços — a documentação usa a palavra fenced, cercado — não é enviado ao navegador de ninguém. É por isso que a documentação diz que você pode buscar dados de uma API privada ali dentro com segurança: o visitante nunca vê aquele código, só o resultado dele.

Por que isso importa exatamente neste projeto. O ADR-0002 proibiu montar os cards de advogado no navegador a partir de um objeto JS — conteúdo primário tem que estar no HTML entregue, senão o Google não indexa e quem está sem pacote de dados não vê nada. O frontmatter do Astro é a resposta exata a essa restrição: você escreve um laço sobre os 6 advogados, e o que sai é HTML com os 6 advogados escritos por extenso.

02 · VocabulárioOs quinze termos, nas duas linguagens

Cada cartão tem a fala natural — como você diria numa conversa — e o fundamento técnico, que é o que está escrito na documentação. Embaixo, a analogia e o termo vizinho de que ele se confunde. Se você consegue traduzir de um lado para o outro sem olhar, pegou.

Build step

Fundamento
Você diria

“Tem uma etapa de montagem: eu rodo um comando e ele cospe a pasta pronta pra subir.”

O fundamento

Processo que roda no seu ambiente e transforma código-fonte em artefatos de entrega. Em Astro, astro build → dist/.

AnalogiaA gráfica. Você entrega o arquivo aberto; ela devolve o impresso. O cliente recebe o impresso, não o arquivo aberto. Não confundaCom servidor. O build roda uma vez, quando você quer. O servidor roda a cada visita. Aqui não há servidor — só arquivos parados.

Renderização no servidor (server-first)

Fundamento
Você diria

“O HTML já chega pronto. O celular não precisa montar nada, só pintar o que recebeu.”

O fundamento

“Websites run faster when they render HTML on the server.” Astro “leverages server rendering over client-side rendering in the browser as much as possible.”

AnalogiaMóvel montado × móvel em caixa. O primeiro você usa ao abrir; o segundo exige chave, manual e meia hora. Não confundaCom build. “Servidor” aqui inclui o build: o ponto é só que não é o celular do visitante que monta.

Zero JS por padrão

JavaScript
Você diria

“Ele não manda JavaScript nenhum, a não ser que eu peça.”

O fundamento

“Zero JS, by default: Less client-side JavaScript to slow your site down.” O resultado é “zero JavaScript footprint added by default”.

AnalogiaUm contrato que começa em branco. Cada cláusula de JS você assina conscientemente, uma por uma. Não confundaCom JS adiado. Zero significa que o arquivo não existe. Adiado significa que ele existe e vai chegar mais tarde — e continua pesando bytes.

Hidratação

JavaScript
Você diria

“O HTML já estava na tela, aí o JavaScript chega e ‘liga’ ele — daí o botão começa a funcionar.”

O fundamento

Processo em que o JS do cliente assume um HTML já renderizado no servidor, anexando estado e ouvintes de evento sem recriar o DOM.

AnalogiaA vitrine da loja já montada, e o vendedor chegando depois para atender. Antes dele, você vê tudo; só não consegue comprar. Não confundaCom renderizar. Renderizar é desenhar na tela. Hidratar é dar comportamento ao que já está desenhado. O intervalo entre os dois é o desconforto do visitante.

Ilha (client island)

JavaScript
Você diria

“A página é estática inteira, menos um pedacinho que se mexe — e só esse pedacinho carrega JavaScript.”

O fundamento

“An island is an enhanced UI component on an otherwise static page of HTML.” “A client island is an interactive JavaScript UI component that is hydrated separately from the rest of the page.”

AnalogiaIlhas num mar de HTML. O mar não precisa de barco; só as ilhas. Não confundaCom qualquer região interativa. Em Astro, “ilha” tem sentido estrito: é um componente de framework (React, Svelte, Vue) com uma diretiva client:. Um <script> solto num .astro não é ilha — veja a seção 07.

Ilha de servidor (server island)

JavaScript
Você diria

“A página inteira fica no cache, e só um quadradinho é buscado na hora — sem JavaScript nenhum.”

O fundamento

“A server island is a UI component that server-renders its dynamic content separately from the rest of the page.”

AnalogiaO jornal impresso com um espaço em branco para o adesivo do dia. Não confundaCom ilha de cliente. As duas “ilham”, mas por motivos opostos: a de cliente resolve interatividade; a de servidor resolve conteúdo que muda. Neste projeto, nenhuma das duas é necessária — o site é 100% estático.

client:* — diretiva de cliente

JavaScript
Você diria

“É onde eu digo quando aquele pedaço deve ganhar vida: já, quando sobrar folga, ou quando o cara rolar até lá.”

O fundamento

“Component attributes that determine when your component's JavaScript should be sent to the browser.” Sem ela, o componente vira HTML estático.

AnalogiaA hora marcada do vendedor. Você não escolhe se ele existe — isso já foi decidido —, escolhe a que horas ele aparece. Não confundaCom otimização automática. É explícito e manual: você digita client:visible no componente. O Astro nunca decide isso por você.

Componente .astro

Arquivos
Você diria

“É um pedaço de HTML que eu escrevo uma vez e reuso — tipo um bloco do Elementor, só que meu.”

O fundamento

“The basic building blocks of any Astro project (…) HTML-only templating components with no client-side runtime.”

AnalogiaUm carimbo. Você desenha o carimbo uma vez e bate 6 vezes na página, trocando o nome a cada batida. Não confundaCom componente React. O .astro não tem estado, não tem ciclo de vida e nunca roda no navegador. É molde, não máquina.

Frontmatter (script do componente)

Arquivos
Você diria

“É o cercadinho de código lá em cima, entre os três tracinhos. O que está ali dentro fica ali dentro.”

O fundamento

Bloco entre --- no topo do arquivo, com JavaScript/TypeScript que roda no build e não é enviado ao navegador. Lugar seguro para segredos e consultas.

AnalogiaA cozinha do restaurante. O cliente come o prato; não vê a panela, a receita nem o preço do fornecedor. Não confundaCom <script>. O frontmatter roda uma vez, na sua máquina. O <script> roda toda vez, no celular dele. Mesma linguagem, dois mundos.

Props e <slot />

Arquivos
Você diria

“Props é o que eu passo pro carimbo mudar — nome, foto, OAB. Slot é o buraco onde eu enfio conteúdo qualquer.”

O fundamento

Props: atributos do componente, lidos via Astro.props, tipáveis. Slots: marcadores <slot /> que recebem o HTML filho, com versão nomeada e conteúdo padrão.

AnalogiaProps são os campos de um formulário impresso. Slot é o envelope: cabe o que você puser dentro. Não confundaUm com o outro. Props carregam dados (uma string, um número). Slot carrega marcação (outros elementos inteiros).

Roteamento por arquivo

Arquivos
Você diria

“A URL é a pasta. Criou o arquivo, nasceu a página — não tem configuração de rota.”

O fundamento

“Pages routes are created for your site by adding supported file types to this directory.” src/pages é obrigatório: “Without it, your site will have no pages or routes!”

AnalogiaA gaveta do arquivo físico. O nome da pasta é o endereço; não existe um índice separado para manter em sincronia. Não confundaCom src/components. Componente não vira URL. Só o que está em src/pages vira página.

<script> dentro do .astro

JavaScript
Você diria

“JavaScript normal, do jeito que eu já escrevo — só que o Astro junta, minifica e coloca uma vez só.”

O fundamento

Por padrão o Astro processa o script: vira type="module", os imports são empacotados, é TypeScript, é deduplicado (um componente usado 6 vezes inclui o script uma vez) e, se for pequeno, é embutido no HTML para poupar uma requisição.

AnalogiaSeu texto passando pelo revisor da editora antes de imprimir: é o seu texto, mas sai padronizado e sem repetição. Não confundaCom ilha. Ilha exige framework de UI instalado e diretiva client:. Isto aqui é JavaScript puro no HTML — e é quase certamente o que este projeto vai usar.

MPA × SPA

Entrega
Você diria

“Cada página é uma página de verdade, e não um aplicativo que finge trocar de tela.”

O fundamento

Astro adota a “Multi-Page App (MPA) approach”. Frameworks como Next, Nuxt e SvelteKit foram “built for client-side rendering”, com “complexity and performance tradeoffs” que penalizam a primeira carga.

AnalogiaLivro × aplicativo de leitura. Virar a página do livro custa zero; o aplicativo precisa carregar antes de virar qualquer coisa. Não confundaCom site antiquado. MPA não é retrocesso — é a escolha certa quando o conteúdo é o produto, que é exatamente o caso de um one-pager de escritório.

<Image /> e <Picture />

Entrega
Você diria

“Eu jogo a foto grande lá dentro e ele cria sozinho todos os tamanhos e formatos.”

O fundamento

Transformam dimensão, formato e qualidade no build; geram srcset responsivo; <Picture /> emite AVIF e WebP com fallback; aplicam loading="lazy" e decoding="async" por padrão; inferem as dimensões, o que evita CLS.

AnalogiaO laboratório fotográfico que revela o mesmo negativo em seis tamanhos, sem você pedir um por um. Não confundasrc/ com public/. Imagem em src/ é processada e otimizada. Em public/ é copiada “as-is, with no processing” — os 36 arquivos do orçamento não aparecem.

dist/ e o hash no nome

Entrega
Você diria

“Cada arquivo sai com um códigozinho no nome; mudou o conteúdo, muda o código — daí dá pra mandar o navegador guardar pra sempre.”

O fundamento

O build escreve em _astro/ com nomes hasheados (_astro/index.DRf8L97S.js), próprios para cache de longo prazo com Cache-Control: public, max-age=31536000, immutable.

AnalogiaNúmero de edição no livro. Enquanto o número não muda, ninguém precisa conferir se mudou algo. Não confundaCom o HTML. O HTML não leva hash e por isso revalida a cada visita — é a decisão 6 do ADR-0002, e é o que permite publicar sem quebrar o cache de quem já visitou.

04 · A comparaçãoAstro contra o resto do front-end

A pergunta “qual a diferença do Astro para as outras tecnologias” tem uma resposta curta: todas montam HTML — a diferença é onde e quando. É isso, e só isso, que o desenho abaixo mostra.

O mesmo em números e consequências, para este projeto
Tecnologia Quem monta o HTML JS enviado por padrão Os 12 lugares que repetem um advogado Encaixe no ADR-0002
HTML à mão Você, no editor Zero 12 blocos duplicados; trocar o nome de um advogado é 12 edições Viola “informação fictícia trocável sem refatoração”
WordPress Servidor PHP + banco, a cada visita Dezenas de KB (jQuery, tema, plugins) Resolvido, via loop do tema Estoura o teto de 15 KB de JS antes da primeira linha sua
React SPA (Vite) O celular do visitante ~130 KB só do runtime Resolvido, mas o conteúdo só existe depois do JS rodar Vedado pelo ADR-0001: conteúdo primário tem que estar no HTML entregue

A própria Astro afirma que sites migrados “load 40% faster with 90% less JavaScript” comparados a alternativas em React — número da casa, não de terceiro independente, e por isso vale como direção, não como promessa. O que não é opinião é o mecanismo: componente .astro não tem runtime de cliente, ponto.

05 · Mapa mentalAstro visto de quem nunca abriu um

Cinco ramos. Clique para abrir. Cada folha traz o nome técnico e, embaixo, o que ela é na sua fala.

Site do Alves Assessoria, feito em Astro
  • src/pages/index.astroA página. Como é um one-pager, esse arquivo praticamente é o site. Obrigatório: sem src/pages não existe página nenhuma.
  • src/layouts/Base.astroO esqueleto que se repete: <head>, o preload da Spectral 600, os metadados. Escrito uma vez.
  • src/components/AdvogadoCard.astroO carimbo do advogado. É ele que apaga as 12 duplicações.
  • src/data/advogados.jsonOs 6 advogados como dado, não como HTML. Trocar um nome fictício por um real vira uma edição, não doze.
  • src/assets/fotos/As fotos originais, grandes. Aqui dentro elas são processadas; em public/ não seriam.
  • public/O que passa direto, sem tratamento: favicon, robots.txt, o _headers da Cloudflare.
  • dist/O resultado. É essa pasta que a Cloudflare publica — e é ela que o ADR-0002 manda versionar no git como seguro contra apodrecimento de dependência.
  • Repetição sem duplicaçãoOs 6 cards e os 6 painéis saem do mesmo componente, alimentados pelo mesmo JSON. O #7 pode mexer no modelo de dados sem que ninguém reescreva HTML.
  • 36 arquivos de imagem, de graça6 fotos × 3 larguras × 2 formatos. <Picture /> gera AVIF e WebP com srcset; ninguém abre o Photoshop 36 vezes.
  • Nada de CLS nas fotosEle lê a dimensão da imagem no build e escreve no HTML. Uma das quatro metas do orçamento (CLS ≤ 0,10) sai quase de brinde.
  • Hash e cache eterno_astro/estilo.a91f.css. Nome muda quando o conteúdo muda — é o que autoriza o immutable da decisão 6.
  • Script deduplicado e embutidoUm <script> num componente usado 6 vezes entra uma vez só; se for pequeno, entra dentro do HTML e economiza uma requisição.
  • Painel do advogado — FLIP na foto~2 KB previstos. Abre e fecha o painel, anima só a foto por transform. Sem framework: <script> no .astro.
  • Animação do mapaOs 4 pinos animam em CSS puro — custo zero de JS. O que sobra de JavaScript aqui é pouco ou nenhum.
  • Service worker~1,5 KB. É o que faz o endereço e o telefone abrirem sem rede. Não é ilha nem componente: é arquivo próprio, registrado por um <script>.
  • Intro de desktopInjetada por JS, nunca presente no HTML — se viesse no HTML e o JS falhasse, o visitante ficaria com tela cheia sobre o site.
  • Nenhuma ilha, provavelmenteIlha exige instalar React/Svelte/Vue. Nada dessa lista precisa disso. O projeto usa Astro sem nunca criar uma ilha — e isso é uso correto, não uso incompleto.
  • O desenhoAstro não tem opinião visual. Layout, cor e tipografia continuam sendo CSS escrito por você — é o #21, e o orçamento é que diz quanto cabe.
  • O orçamentoEle facilita caber, mas não impede estourar. O gate que bloqueia o PR conferindo o tamanho do dist/ é coisa sua, não dele.
  • AcessibilidadeContraste, ordem de foco, prefers-reduced-motion: nada disso vem pronto. Astro entrega o HTML que você escreveu, inclusive o ruim.
  • Conteúdo e OABO que pode ser dito num site de advocacia é pesquisa do projeto, não característica de framework.
  • O apodrecimento do NodeDaqui a alguns anos o npm install pode não rodar. É custo assumido; a mitigação é o dist/ versionado.
  • Os três traçosOnde termina o que roda na sua máquina e começa o que vai para o celular. Se você tem isso, tem o Astro.
  • Componente + propsEscrever o carimbo e passar dados para ele. É 80% do trabalho real deste site.
  • <Image /> e <Picture />Porque as fotos são a maior linha variável do orçamento, e essa é a única parte da stack que mexe nelas.

06 · Na práticaAs 12 duplicações, em quinze linhas

Este é o arquivo que faz o trabalho. Leia de cima para baixo e repare onde está a fronteira.

---
// ↑ daqui até os próximos três traços: roda na SUA máquina, uma vez.
//   nada disto é baixado pelo visitante.
import advogados from '../data/advogados.json';
import AdvogadoCard from '../components/AdvogadoCard.astro';
import Base from '../layouts/Base.astro';

const emAtividade = advogados.filter(a => a.ativo);
---

<!-- ↓ daqui para baixo: isto VIRA HTML e é o que atravessa a rede -->
<Base titulo="Alves Assessoria">
  <section id="advogados">
    {emAtividade.map(a => <AdvogadoCard {...a} />)}
  </section>
</Base>

Seis advogados no JSON viram seis cards no HTML de saída — escritos por extenso, com nome, OAB e biografia, exatamente como o Google precisa e como quem está sem pacote de dados precisa. O map não vai junto. Ele já terminou o trabalho dele antes do arquivo existir.

Trocar o nome fictício “Dra. Fulana” pelo nome real de uma advogada é uma linha do JSON. Sem o build step, seriam doze edições espalhadas — e a restrição permanente do mapa (“toda informação fictícia precisa ser trocável sem refatoração”) estaria quebrada na prática, ainda que respeitada no papel.

07 · As armadilhasQuatro lugares onde isso te engana

1. Confundir <script> com ilha

Este é o erro de vocabulário mais provável no seu caso, e ele já apareceu: o ADR-0002 diz que “o modelo de ilhas casa com as duas ilhas que de fato existem — painel do advogado e mapa”. Na linguagem estrita do Astro, isso não é bem verdade: ilha exige um framework de UI instalado (React, Svelte, Vue) e uma diretiva client:. Painel e mapa vão ser <script> em .astro — JavaScript puro, processado e deduplicado pelo Astro, mas não ilha.

Isso invalida a decisão? Não. O que a decisão diz de substantivo — “existem duas regiões interativas e só elas precisam de JS” — continua exatamente certo, e a escolha do Astro continua bem fundamentada. O que muda é a palavra. Vale corrigir no ADR, porque “ilha” aqui está sendo usada no sentido frouxo de “região interativa”, e um leitor futuro pode entender que o projeto instala React — que é o oposto do que o orçamento quer.

2. Achar que client:visible é sempre a opção econômica

É a de menor prioridade, e serve para “elementos abaixo da dobra ou tão pesados que você preferiria não carregá-los se o usuário nunca os vir”. Mas o padrão que ela convida — esconder o conteúdo até o JavaScript chegar — é expressamente proibido pelo ADR-0002: nada de estado inicial invisível dependente de JS. Com 24% dos usuários rurais não conseguindo abrir aplicativo nenhum ao fim do pacote, “o site abriu mas o texto não apareceu” é o pior desfecho disponível.

3. Botar a foto em public/

Funciona, a foto aparece, e o orçamento estoura em silêncio: public/ é copiado “as-is, with no processing”. Nada de AVIF, nada de srcset, nada de 70 KB por retrato. Regra prática: foto de conteúdo em src/; só ícone e arquivo de configuração em public/.

4. Instalar React “só para um componentezinho”

client:only é a diretiva que mais parece inofensiva e é a mais cara: ela “skips HTML server rendering, and renders only on the client”. Ou seja, aquele pedaço não existe no HTML entregue — que é precisamente o que o ADR-0001 veda para conteúdo primário. Se algum dia ela parecer necessária, a pergunta certa é por que o conteúdo não pode ser servido pronto.

08 · A rotaComo aprender isto, em quatro sessões curtas

Cada etapa termina num ganho verificável — algo que você vê acontecer, não algo que você acredita ter entendido. Nenhuma exige tocar no site de verdade.

1

Ver a fronteira com os próprios olhos

Rode npm create astro@latest, escolha o modelo mínimo, rode npm run build e abra o dist/index.html num editor de texto. Depois procure por qualquer arquivo .js dentro de dist/.

Ganho: você vai encontrar HTML completo e nenhum JavaScript. A frase “zero JS por padrão” deixa de ser slogan.

2

Fazer o carimbo

Crie um AdvogadoCard.astro com três props (nome, OAB, área) e renderize-o seis vezes a partir de um array escrito na própria página. Depois mude o array e reconstrua.

Ganho: as 12 duplicações do projeto deixam de ser um problema em aberto. Esta é a etapa que carrega 80% do valor.

3

Soltar as imagens no pipeline

Ponha uma foto pesada em src/assets/, use <Picture /> com AVIF e WebP, reconstrua e olhe o dist/. Compare com a mesma foto posta em public/.

Ganho: você vê os 36 arquivos nascerem, e vê a versão em public/ não nascer. A linha de 70 KB por foto vira algo controlável.

4

Escrever o único JavaScript que este site precisa

Um <script> dentro do componente que abre e fecha o painel. Reconstrua e meça o tamanho do .js gerado contra o teto de 15 KB.

Ganho: o orçamento do ADR-0002 deixa de ser tabela e vira número que você produziu. É a partir daqui que “otimizado” é verificável por você.

09 · RecuperaçãoCinco perguntas, sem consultar acima

Responder de memória é o que fixa. Errar aqui é barato — errar no build, não.

Por que um componente .astro não envia JavaScript ao navegador?

A documentação é literal: são “HTML-only templating components with no client-side runtime” e “don't render on the client”. Não há adiamento — há ausência. As outras três respostas descrevem coisas que o Astro sabe fazer, mas nenhuma delas é a razão.

Qual é a diferença real entre client:load e client:idle?

A diretiva decide quando o JavaScript é enviado, nunca quanto. É por isso que trocar de diretiva não te ajuda a caber nos 15 KB: para o orçamento, adiar e não adiar dão no mesmo.

Um <script> escrito dentro de um .astro é uma ilha?

Ilha é termo estrito: componente React/Svelte/Vue com client:*. O <script> é JavaScript comum — processado, empacotado e deduplicado pelo Astro, mas sem framework por trás. É por isso que este projeto pode não ter nenhuma ilha.

Onde deve ficar a foto de um advogado, e por quê?

Imagem em src/ é transformada, otimizada e empacotada. Em public/ é copiada “as-is, with no processing”. Como as fotos são a maior linha variável do orçamento, essa escolha de pasta é uma decisão de bytes, não de organização.

Por que o HTML do site não leva hash no nome, e os outros arquivos levam?

Os assets com hash podem ser guardados por um ano (immutable) porque, se mudarem, mudam de nome. Alguém precisa avisar o navegador dos nomes novos — e esse alguém é o HTML, que por isso revalida a cada visita. É a decisão 6 do ADR-0002, e agora ela tem mecanismo, não só regra.

A fonte primária, se você ler só uma coisa

Astro Docs — Islands architecture. São dez minutos, e é o texto que responde diretamente a pergunta que você fez. Depois dele, Components — a página onde está a frase sobre “no client-side runtime”. Se quiser a origem histórica da ideia, o termo “Component Islands” foi cunhado por Katie Sylor-Miller, arquiteta de front-end da Etsy, em 2019, e escrito por Jason Miller em Islands Architecture.
